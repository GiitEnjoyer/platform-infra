# ADR-0002: VictoriaMetrics вместо Prometheus + Thanos

**Статус:** принято

## Контекст

Около 3 млн активных временных рядов (кластер, ingress при 50k RPS, бизнес-метрики), требуемое хранение — 90 дней. Prometheus в одном экземпляре на таком объёме требует 30+ ГБ RAM; долгосрочное хранение требует Thanos или Mimir с объектным хранилищем, компактором и querier.

## Решение

`victoria-metrics-k8s-stack`: vmagent для сбора, VictoriaMetrics single-node для хранения, vmalert и Alertmanager для алертинга, Grafana.

## Обоснование

- Потребление памяти и диска на тот же объём рядов в несколько раз ниже (сжатие, отсутствие WAL-реплея при рестарте).
- 90 дней хранения без дополнительных компонентов.
- Совместимость по PromQL и CRD: существующие ServiceMonitor и PrometheusRule конвертируются оператором автоматически, дашборды не меняются.
- Переход на кластерную версию (vminsert/vmselect/vmstorage) возможен без изменения клиентов, если single-node перестанет справляться.

## Последствия

- `−` Single-node — единая точка отказа хранилища метрик. Принято: при недоступности VictoriaMetrics алерты Watchdog перестают приходить в Opsgenie, срабатывает heartbeat; vmagent буферизует данные на диске до восстановления.
- `−` Команда должна знать отличия MetricsQL (например, обработку `rate` на границах окна).
