# ADR-0001: Terragrunt для управления окружениями

**Статус:** принято

## Контекст

Инфраструктура описывается Terraform-модулями, окружений минимум два (dev, prod) с одинаковой топологией и разными размерами. Нужны: отдельный state на каждый стек, единые настройки backend и провайдера, явные зависимости между стеками, возможность пересоздать окружение одной командой.

## Рассмотренные варианты

1. **Terraform workspaces.** Один state-бэкенд и код на все окружения; различия — через `terraform.workspace` в условных выражениях. Минусы: условная логика расползается по модулям, нет изоляции стеков, легко применить к prod по ошибке.
2. **Каталог на окружение с копией корневого модуля.** Прозрачно, но backend/provider и вызовы модулей дублируются, окружения расходятся со временем.
3. **Terragrunt.** Корневой `root.hcl` генерирует backend и provider; `_envcommon` описывает вызов модуля один раз; окружение задаёт только значения.

## Решение

Terragrunt (вариант 3).

## Последствия

- `+` Добавление окружения — новый каталог с `env.hcl` и тремя файлами по 8 строк.
- `+` `run-all` строит граф по `dependency` и применяет независимые стеки параллельно; на этом основано развёртывание тестового окружения за ~15 минут.
- `+` `mock_outputs` позволяют выполнять `plan` в MR до создания зависимых стеков.
- `−` Дополнительный инструмент в CI и у инженеров; версии Terraform и Terragrunt зафиксированы в `.gitlab-ci.yml`.
- `−` Ошибки в HCL-функциях Terragrunt видны только при запуске; закрыто `hclfmt` и `plan` на каждый MR.
