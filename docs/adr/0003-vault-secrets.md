# ADR-0003: HashiCorp Vault для секретов приложений и CI

**Статус:** принято

## Контекст

Секреты хранились в переменных GitLab CI и Kubernetes Secret, создаваемых вручную. Проблемы: нет аудита доступа, ротация требует ручного обновления в нескольких местах, Kubernetes Secret в etcd доступен любому с правом `get secrets` в namespace.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| Sealed Secrets | Простота, секреты в Git | Ротация через перешифровку и коммит, нет динамических секретов |
| External Secrets + Lockbox | Managed-сервис | Привязка к одному облаку, секрет всё равно оказывается в Kubernetes Secret |
| **Vault + Agent Injector** | Аудит, политики на путь, Kubernetes/JWT auth, динамические секреты | Нужно эксплуатировать HA-кластер Vault |

## Решение

Vault в HA-режиме (Raft, 3 реплики по зонам) с auto-unseal через Yandex KMS.

- Приложения: Kubernetes auth, роль на ServiceAccount, политика read-only на свой путь; секреты рендерятся Vault Agent в файл в поде.
- CI: JWT auth GitLab (`CI_JOB_JWT_V2`), токен живёт время работы job; роль ограничена `project_path` и `ref_protected`.
- Terraform пишет сгенерированные пароли БД сразу в Vault.

## Последствия

- `+` Ротация пароля — одна операция в Vault; поды получают новое значение без передеплоя (Agent перечитывает шаблон).
- `+` Аудит-лог всех чтений.
- `−` Vault становится критическим компонентом: старт новых подов зависит от него. Смягчение: 3 реплики в разных AZ, алерт на `vault_core_unsealed == 0`, runbook восстановления из Raft-снапшота.
